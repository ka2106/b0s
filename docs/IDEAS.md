### 1. Дерево «объект → этапы»

**Проблема.** Реестр — плоский список из 185 строк: каждый этап отдельной строкой, название
объекта повторяется. Объектов 78, у некоторых по 5–6 этапов; «как дела у Краснодара» приходится
собирать глазами.

**Как будет выглядеть.**

```
▼ Краснодар          45 300,10   1 250 000,00   4 этапа · 2 АБЧ   сдано 1
    └ 1 этап         45 300,10     280 000,00   Утрачен           05.12.2022
    └ 2 этап                                      …
      Корпус АБЧ
```

- строка объекта: название, суммарная площадь, счётчик «этапов / АБЧ», сколько сдано;
- строки этапов с отступом, прежние колонки (даты, статусы, ссылки);
- треугольник сворачивает объект; в свёрнутом виде 78 строк вместо 185.

**Что меняется в коде.**

- `renderTable` строит группы по `r.obj` вместо плоского списка; строка-родитель получает
  класс `.row-group` и `aria-expanded`;
- состояние свёрнутости — `Set` в памяти + `localStorage` (переживает перезагрузку);
- **итоги считают только этапы**: родительские строки исключаются, иначе площадь объекта
  складывается с площадью его же этапов;
- поиск и фильтры применяются к этапам; объект показывается, если есть совпадения (в строке
  объекта — «2 из 5 этапов»), и раскрывается автоматически;
- сортировка: объекты сортируются по агрегату (сумма площади или ближайшая дата), внутри —
  по тому же ключу; это нужно описать в интерфейсе, иначе сортировка «ведёт себя странно»;
- печать/PDF: перед печатью раскрывать всё (`beforeprint`), после — возвращать как было;
- экспорт в Excel остаётся плоским, дерево — только вид.

**Варианты поведения.**

| Вариант | Плюс | Минус |
|---|---|---|
| A. Переключатель «Список / Дерево», по умолчанию список | Ничего не меняется для привыкших | Нужно заметить новую кнопку |
| B. По умолчанию дерево, переключатель в список | Польза видна сразу | Меняется привычный вид |
| C. Всегда дерево | Проще код | Нет пути назад; плоский список иногда нужен |

**Оценка:** 4–6 часов: рендер и итоги ~2 ч, состояние ~0,5 ч, печать ~0,5 ч,
клавиатура/aria ~0,5 ч, проверки ~1 ч.
**Риски:** двойной счёт в итогах; сломанная печать; неожиданное поведение сортировки.
**Проверить:** 185 строк / 78 объектов, итоги совпадают с суммой этапов, печать содержит все
строки, поиск фильтрует и раскрывает.

### 2. Кластеры и фильтры на карте

**Проблема.** 69 отдельных меток накладываются друг на друга на общем виде страны; карта
игнорирует фильтры — `updateMap` использует `state.rawData`, поэтому «только ФО Юг» на карте
невозможно.

**Кластеры.**

- `ymaps.Clusterer` вместо `GeoObjectCollection`: на мелком зуме одна метка с числом объектов,
  при приближении распадается на текущие круговые диаграммы;
- иконка кластера — SVG data-URI с числом, в нашей палитре; DOM-шаблоны на метку не
  использовать (запрет из `HANDOVER` — из-за прошлых фризов);
- клик по кластеру — приближение к его границам; в балуне — объекты, этапы, площадь;
- кэш по `signature` сохраняется: если данные не менялись, слой не пересобирается.

**Фильтры.**

| Вариант | Как выглядит | За / против |
|---|---|---|
| A. Общие с таблицей | На карте те же чипы «Выборка» и «Сбросить всё» | Один источник правды; надо решить про поиск |
| B. Отдельные для карты (ФО + год) | Свои селекты в шапке карты | Проще, но два независимых состояния путают |
| C. Только кластеры | Минимум работы | Карта продолжает расходиться с таблицей |

Рекомендация: **A** + подпись «на карте: N объектов · M этапов · X м²» и список объектов
без координат (уже есть).

**Оценка:** 3,5–4,5 часа: кластеры ~2–3 ч, фильтры ~1 ч, чипы и подпись ~0,5 ч.
**Риски:** производительность при зуме (новая нагрузка); дизайн кластеров; клик и балун;
лимит загрузок карты не меняется.
**Проверить:** метки на z≥7, кластеры на z3–5, счётчики совпадают с таблицей при тех же
фильтрах, `?debug=1` — fps и long tasks при зуме.
